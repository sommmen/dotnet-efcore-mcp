# Roslyn-compiled `UserQuery` execution

[← Back to Development Guide](../../DEVELOPMENT.md)

Code: `src/DotnetEfCoreMcp.Server/Querying` (rewritten) + new `src/DotnetEfCoreMcp.Server/Compilation` ·
Tests: `tests/DotnetEfCoreMcp.Server.Tests/Querying` + new `tests/DotnetEfCoreMcp.Server.Tests/Compilation`

> **Status: current `run_query` model.** The Roslyn compilation pipeline (`Compilation/`) and its
> executor (`Querying/RoslynQueryExecutor.cs`) define the supported `run_query` behavior described
> in the public docs: LINQPad-style `UserQuery : TDbContext`, expression or statement-mode authoring,
> default no-tracking, and out-of-process execution options.

## Why

[Query execution](./query-execution.md) currently parses the `run_query` string through
`System.Linq.Dynamic.Core`'s `DynamicExpressionParser`. That parser is not C# — it is a
separate, narrower expression-string grammar that must be hand-mapped to `Queryable`'s generic
method overloads. This has hit a hard wall:

- **`Join`, `GroupJoin`, `SelectMany`, and `Zip` cannot be supported.** These operators need two
  independently-scoped lambda parameters resolved against generic overloads the string parser
  cannot disambiguate. This isn't a policy choice we made — it's a parser limitation, documented
  as a permanent restriction in `query-execution.md`.
- **Every new operator is a bespoke reflection+allowlist exercise.** `QueryExecutor` hand-builds
  `LambdaExpression`s and resolves specific `MethodInfo` overloads per operator
  (`OrderByMethod`, `AsNoTrackingMethod`, etc.). Supporting new shapes (custom projections with
  anonymous types spanning multiple navigations, `let`-style intermediate bindings, local
  functions, multi-statement query construction) means writing more parser/expression-tree glue,
  not just relaxing a filter.
- **It only ever approximates "a query."** Real LINQPad connects a query to a real compiled
  class deriving from the data context (see the attached reference notes, summarized below) so
  the query author gets the *entire* C# language and the *entire* context surface — arbitrary
  `Select` projections, helper LINQ operators, `Database`, `ChangeTracker`, `Set<T>()`, and (where
  enabled) `SaveChanges()`. Trying to keep chasing that surface through a string-expression parser
  is a losing, ever-growing effort.

The user has asked to match LINQPad's actual mechanism instead of continuing to extend the
allowlisted string parser, and has explicitly authorized relaxing today's safety model as far as
necessary to get there — see [Safety model](#safety-model) for where that line is drawn and why.

## How LINQPad actually does it (reference model)

Summarized from the attached notes (`linqpad-query-context.md`) plus linqpad.net's EF Core docs:

1. When a connection is an EF Core connection, LINQPad generates a real C# source file defining
   `class UserQuery : YourDbContext { void Main() { /* your query text, verbatim */ } }` (LINQPad
   calls the query-editor content "Main" for a statements-style query; a single expression like
   `Orders.Where(...)` is wrapped as an expression-bodied equivalent).
2. It compiles that source with the C# compiler against the target assembly (so `YourDbContext`,
   entity types, and any of your own project types are directly visible) plus its own runtime
   helper assembly and a curated set of BCL assemblies.
3. It loads the compiled assembly, instantiates `UserQuery`, and invokes the entry point. Because
   `UserQuery` *inherits* from `YourDbContext`, unqualified identifiers like `Orders` resolve via
   normal C# member lookup to `this.Orders` — no injection, no parser, no allowlist: it's just
   inheritance and real overload resolution.
4. `GetType()` inside the query returns `UserQuery`, not `YourDbContext` — a directly observable
   side effect of the inheritance trick that we should keep in mind (see
   [Behavioral parity notes](#behavioral-parity-notes)).
5. LINQPad's `.Dump()` is its output/materialization hook; our equivalent is the existing
   materialize-and-shape pipeline in `QueryExecutor`/`ToonToolResultFormatter` — the plan re-uses
   that, it does not need a `.Dump()` analog because the tool always returns exactly one JSON/TOON
   result.

We are adopting steps 1–3 directly. Step 4's implication is called out explicitly so it doesn't
surprise anyone debugging `GetType()`-sensitive query code later.

## Target architecture

### 1. Source generation

Given the caller's `query` string (kept as a single expression or a small statement block — see
[Request shape](#request-shape-mostly-unchanged)) and the resolved `DbContext` CLR type
(`TContext`), synthesize a compilation unit:

```csharp
// <auto-generated/> — not persisted; exists only in the in-memory Roslyn compilation.
namespace DotnetEfCoreMcp.Server.CompiledQueries;

public sealed class UserQuery_{token} : global::Fully.Qualified.TContext
{
    public UserQuery_{token}(global::Microsoft.EntityFrameworkCore.DbContextOptions options)
        : base(options)
    {
    }

    public object? RunUserAuthoredQuery()
    {
        return /* caller expression */;
        // or, for a statement-block request:
        // { caller statements; return <lastExpressionOrExplicitReturn>; }
    }
}
```

Notes:
- `{token}` is a per-request GUID/counter so repeated compiles never collide inside the same
  collectible `AssemblyLoadContext` generation (matters if we ever keep more than one compiled
  query alive at once, e.g. for future caching — see [Caching](#compiled-query-caching-later)).
- The generated class takes `DbContextOptions` (non-generic) in its constructor and forwards to
  `base(options)`. This works whether `TContext`'s own constructor is `DbContextOptions<TContext>`
  or the non-generic base type, because EF Core's generated/derived-context constructors are
  compatible with either — we already build a working `DbContextOptionsBuilder` for `TContext` in
  `DbContextDiscovery`/`DbContextActivator` today and can reuse that exact options instance instead
  of re-deriving construction logic.
  - **Fallback for parameterless/`OnConfiguring`-based contexts:** some target contexts (see
    `DbContextDiscovery`'s existing "configured via `OnConfiguring`" case) have no
    `DbContextOptions`-accepting constructor at all. For those, generate a parameterless
    constructor for `UserQuery_{token}` that just calls `base()` and skip passing options — the
    context configures itself exactly as it does for direct instantiation today.
- The method body is emitted **verbatim** from caller input — no string-escaping/rewriting of the
  user's LINQ, because it is now real C#, not an expression-string being reinterpreted. This is
  the direct payoff of the rewrite: whatever compiles is supported, full stop.
- We do not reference/emit a `Main()` void method like LINQPad; `RunUserAuthoredQuery()` returns
  `object?` so both sequence and scalar results flow through one path, mirroring today's
  `QueryResult`/scalar-vs-sequence handling.

### 2. Compilation

Use `Microsoft.CodeAnalysis.CSharp` (`CSharpCompilation`, **not** `CSharpScript`/the scripting
API). Reasons to prefer full `CSharpCompilation` over `Microsoft.CodeAnalysis.CSharp.Scripting`:
- Scripting's implicit "top-level statements + globals object" model doesn't map cleanly onto "a
  class that inherits from an arbitrary runtime-resolved `Type`" — inheritance requires it to be
  a real class declaration, which is exactly what non-scripting `CSharpCompilation` does well.
- Full compilation gives us one `CompilationUnitSyntax` we fully control, so diagnostics map
  directly back to the caller's query text with a fixed, known line offset (needed for
  [Error sanitization](#error-sanitization)).
- No extra `Microsoft.CodeAnalysis.CSharp.Scripting` package/dependency surface; only
  `Microsoft.CodeAnalysis.CSharp` (which brings in `Microsoft.CodeAnalysis` transitively) is
  needed.

Compilation inputs:
- **Parse options:** `CSharpParseOptions` pinned to the latest C# language version the target
  TFM supports (`LanguageVersion.Latest`, net10.0 today), `DocumentationMode.None` (we don't need
  doc-comment binding, keeps compile fast).
- **References:** a curated `List<MetadataReference>`, not "everything loaded in the process."
  This is the primary safety lever now that the query itself is unrestricted C#
  (see [Safety model](#safety-model)):
  - The loaded target assembly (`LoadedAssemblyHandle.Assembly`) and, transitively, whatever it
    needs — reuse `TargetAssemblyLoadContext`'s already-resolved dependency set instead of
    re-resolving from scratch (see [AssemblyLoadContext reuse](#assemblyloadcontext-reuse)).
  - Our own EF Core package assemblies (`Microsoft.EntityFrameworkCore`, `.Relational`,
    whichever provider matches the active connection) — these must be the **same identity**
    copies the target assembly resolves against, which `TargetAssemblyLoadContext`'s existing
    "shared assembly" allowlist already guarantees (see the class's doc comment on why
    `DbContext` type identity must match).
  - A small, explicit BCL allowlist (`QueryCompiler.BuiltInReferenceAssemblyNames`):
    `System.Private.CoreLib`, `System.Runtime`, `System.Linq`, `System.Linq.Queryable`,
    `System.Linq.Expressions`, `System.Collections`, `System.ObjectModel`,
    `System.ComponentModel.TypeConverter` (required because `DbSet<T>` implements
    `IListSource`). This is intentionally **not** "every assembly this process has loaded" — see
    the exclusions below.
  - Deliberately **excluded by default**: `System.IO*`, `System.Net*`, `System.Diagnostics.Process`,
    `System.Reflection.Emit*`, `System.Runtime.Loader`. A query author who is not given a
    `MetadataReference` to `System.Net.Http.dll` cannot call it — omission is enforced entirely by
    absence from the reference list; the compiler will fail to bind the identifier, which
    produces an ordinary (sanitized) compile diagnostic, not a runtime exception. This is a compile-
    time control, cheaper and more reliable than trying to sandbox already-running IL.
  - **Assembly omission alone is not sufficient**, and is backstopped by a semantic check (see
    [Safety model](#safety-model)): several of the types the reference-omission list above is
    meant to block — notably `System.IO.File` (defined in the reference-assembly-pack copy of
    `System.Runtime`) and `System.Reflection.Emit.AssemblyBuilder` (defined directly inside
    `System.Private.CoreLib`) — are physically implemented in assemblies that must always be
    referenced for *any* query to compile. Omitting an assembly reference cannot exclude a type
    that lives inside an assembly you cannot omit.
  - This list is server-side configuration
    (`QueryCompilation:AdditionalReferenceAssemblyNames`, empty by default), not caller-suppliable
    — a request can never add references. This mirrors the existing "no per-request override of
    security-relevant caps" convention used for `MaxTake` et al.
- **Compilation options:** `OutputKind.DynamicallyLinkedLibrary`,
  `nullableContextOptions: NullableContextOptions.Disable` (don't force the query author to
  satisfy nullable-reference warnings-as-errors; keep this a correctness surface, not a style
  gate), `optimizationLevel: OptimizationLevel.Release`, `allowUnsafe: false` (**hard-blocked** —
  `unsafe` is the one construct that can subvert the reference-list containment strategy above by
  reaching arbitrary memory, so it stays off even though everything else is deliberately
  permissive per the user's direction).

Emit to an in-memory `MemoryStream` (`compilation.Emit(peStream)`), no temp files on disk —
matches the "server-side, ephemeral, no artifacts left behind" posture of existing tools like
`preview_query_sql`.

### 3. Loading and execution

- Reuse the existing collectible-`AssemblyLoadContext` pattern
  (see [AssemblyLoadContext reuse](#assemblyloadcontext-reuse)) rather than inventing a second
  loading mechanism: load the compiled bytes into a **new, dedicated, collectible** `AssemblyLoadContext`
  per request (a query-scoped ALC, distinct from the long-lived `TargetAssemblyLoadContext` that
  holds the target project's own assembly), with a `Resolving` handler that falls back to the
  target's already-loaded assembly and the shared/default-context BCL and EF Core assemblies. One
  ALC per query keeps unload granularity at the request level: a single query's compiled assembly
  can be unloaded the moment it finishes, independent of the target assembly's lifetime.
- Instantiate `UserQuery_{token}` via `Activator.CreateInstance(type, options)` (or the
  parameterless overload for the `OnConfiguring` fallback case), call `RunUserAuthoredQuery()`,
  and route the returned `object?` through the **same** post-processing `QueryExecutor` already
  has: `AsNoTracking` semantics (see [AsNoTracking under real C#](#asnotracking-under-real-c)),
  deterministic ordering injection, default/clamped `Take`, scalar-vs-sequence detection,
  row-shape projection, and `hasMoreRows` (once P0 #2 lands) — none of that materialization
  contract changes; only *how the queryable/scalar is produced* changes.
- Always dispose the `UserQuery_{token}` instance (it's a `DbContext`) and then unload its ALC in
  a `finally`, exactly mirroring `LoadedAssemblyHandle.Unload()`'s "unload is GC-driven, don't
  retain `Type`/`Assembly` references past unload" contract — the query executor must not cache
  `Type`s or reflection handles from a per-request compiled assembly beyond the request.
- Timeouts/cancellation: pass the existing per-connection command-timeout `CancellationToken`
  through to `RunUserAuthoredQuery()`'s materialization step exactly as today. Add a **separate,
  short, non-configurable compile timeout** (e.g. 5s) around the `CSharpCompilation.Emit` call —
  compiling untrusted, possibly deliberately-pathological C# (e.g. exponential generic-constraint
  blowups) is its own denial-of-service surface distinct from query execution time.

### AssemblyLoadContext reuse

`TargetAssemblyLoadContext` already solves the two hardest parts of this problem for the *target*
assembly: (a) resolving the target's own dependencies via `AssemblyDependencyResolver` +
`TargetDependencyProbe`, and (b) sharing EF Core/Identity assembly *identity* with the default
context so `typeof(DbContext).IsAssignableFrom(...)` and friends work correctly across the ALC
boundary. The query-scoped ALC for a compiled `UserQuery_{token}` assembly needs exactly the same
sharing behavior (it must see the *same* `DbContext`/entity types the target assembly and the
server both see), so it should be implemented as a sibling class — e.g. `CompiledQueryLoadContext`
in the new `Compilation` folder — that copies `TargetAssemblyLoadContext`'s "shared assembly
names" allowlist and its default-context `Resolving` fallback, but does not need
`TargetDependencyProbe`'s NuGet-cache/probing-root logic, because a compiled query assembly only
ever references assemblies we already resolved once for the target
(no new, not-yet-resolved dependencies can appear — the reference list is closed by construction
in [step 2](#2-compilation)). Consider extracting the shared-assembly-name list and
default-context fallback logic into a small shared base type both `TargetAssemblyLoadContext` and
`CompiledQueryLoadContext` derive from, to avoid duplicating that allowlist in two places.

### Request shape (mostly unchanged)

Keep the `run_query(contextName, query, connectionName?)` tool signature. `query` now compiles as
real C# rather than a parser-specific expression grammar. Two authoring modes, both compiled the
same way:

- **Expression mode:** `query` is a single C# expression, wrapped as `return <query>;` inside
  `RunUserAuthoredQuery()`. Ordinary LINQ fragments stay concise in this form.
- **Statement mode:** if `query`'s trimmed text ends with `;` or contains a top-level `{`, treat
  it as a statement block body instead of a single
  expression, e.g. `var recent = Orders.Where(o => o.Created >= DateTime.Today.AddDays(-30)); return recent.Join(Customers, o => o.CustomerId, c => c.Id, (o, c) => new { o.Id, c.Name });`
  This is what actually unlocks `Join`/`GroupJoin`/`SelectMany`/`Zip` and multi-step queries with
  intermediate `var` bindings — the exact class of query the Dynamic-LINQ parser could never
  represent.

No other tool-facing parameter changes. The `contextName`/`connectionName` resolution, connection
policy checks (production/`ReadOnly` enforcement), and result formatting are unaffected by this
rewrite.

### AsNoTracking under real C#

Today, `QueryExecutor` injects an `AsNoTracking()` call into the built expression tree
programmatically. With real compiled C#, the query author's code can already call
`.AsNoTracking()`/`.AsTracking()` explicitly, or not call either. To preserve the "always
read-only" guarantee without relying on the caller to opt in:
- Configure the `UserQuery_{token}`'s `DbContextOptionsBuilder` with
  `UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking)` as the context-level default
  (set alongside the other options already built for the resolved connection, e.g. command
  timeout) instead of rewriting the query's expression tree. This is a strictly better mechanism
  than expression-tree injection: it's the officially supported EF Core knob for exactly this
  scenario, and it means an explicit `.AsTracking()` call in caller code (if the query author adds
  one) would win, which is desired — see [Change tracking / mutation scope](#change-tracking--mutation-scope--saveChanges)
  for why we don't want to silently override an explicit opt-in.
- `SaveChanges()`/`SaveChangesAsync()` reachability is a policy decision, not a mechanism
  limitation — see the next section.

### Change tracking / mutation scope / `SaveChanges()`

Because `UserQuery_{token} : TContext` inherits the *entire* context surface, `SaveChanges()`,
`Add()`, `Remove()`, `Update()`, `ChangeTracker`, and `Database.ExecuteSqlRaw(...)` are all
reachable from query code the moment tracking is enabled for an entity — this is a direct,
unavoidable consequence of the inheritance model (it is also exactly how LINQPad's own EF Core
driver behaves; the reference notes show `SaveChanges()` as explicitly available).
`run_query` is documented as read-only by default, and the current implementation keeps that
promise by **gating writes at the policy layer, not by trying to strip members from the
compiled surface**:
- Keep `UseQueryTrackingBehavior(NoTracking)` as the default (previous section) — with no
  tracked entities, `SaveChanges()` is a no-op even if called, for the common case of a query that
  never explicitly re-attaches/tracks something.
- Add an explicit runtime guard: override `SaveChanges`/`SaveChangesAsync` on
  `UserQuery_{token}` itself, since it's a real subclass we control, and throw a sanitized
  `QueryExecutionException` unless the active
  connection is non-production `ReadWrite` **and** `QueryExecution:AllowMutationsInRunQuery`
  flag (default `false`) is enabled — mirroring the exact gating shape already used for
  `EntityMutations:Enabled` in [Structured mutations](./mutations.md). This keeps `run_query`
  read-only by default while leaving a clearly-labeled, explicitly opt-in escape hatch for the
  cases where a caller genuinely wants LINQPad-style ad hoc mutation scripts — which is a
  reasonable long-term destination given the user's stated goal ("we can support a whole area of
  things") but should not be the default behavior of an existing, documented-as-read-only tool.
- This guard is generated into `UserQuery_{token}`'s source (an `override` calling back into a
  small runtime helper with the resolved policy decision), not bolted on after compilation, so it
  cannot be bypassed by clever query code — the override is part of the type itself.

### Error sanitization

Compile diagnostics (`CSharpCompilation.GetDiagnostics()`) can legitimately contain fragments of
the caller's own query text (e.g. "CS0103: The name 'Foo' does not exist..."), which is fine to
return — it's the caller's own input, not secret. What must stay sanitized, exactly as today:
- Never include target assembly file paths, the compiled-query's synthesized namespace/class
  name, connection strings, or provider exception internals in a returned diagnostic.
- Map `CSharpCompilation` diagnostics' line/column back to the caller's original `query` text
  (subtract the fixed header-line offset introduced by the generated class wrapper) so error
  messages reference "your query, line N" rather than the internal generated file's line number.
- Runtime exceptions during execution continue to flow through the exact same
  `QueryExecutionException`-wrapping/sanitization path `QueryExecutor` already uses today (see
  `query-execution.md`'s existing conventions on stack traces, connection strings, and provider
  internals never being disclosed) — this part of the contract is unchanged by the rewrite.

## Safety model

The user explicitly authorized relaxing today's constraints to get here, so this section states
plainly what is deliberately **removed** versus what is **kept** as a hard boundary, and why each
kept boundary earns its place.

**Removed / relaxed (by design):**
- The Dynamic-LINQ operator allowlist is gone — arbitrary LINQ operator chains, custom
  projections, local `var` bindings, and multi-statement query bodies are all permitted.
  `Join`/`GroupJoin`/`SelectMany`/`Zip` become fully supported.
- The single-statement-only restriction is gone (statement-block mode, above).
- Reflection is not specially blocked at the language level — `typeof`, `GetType()`, etc. compile
  fine; there's no value in blocking them since they can't reach anything not already reachable
  via the reference list.

**Kept as hard boundaries (still enforced, and why):**
- **The reference list stays curated and non-caller-overridable**, as defense-in-depth: assemblies
  that are cleanly excludable (`System.Net.Http`, `System.Diagnostics.Process`'s own assembly,
  etc.) never even get supplied to the compiler as a `MetadataReference`, so nothing exposes them.
- **A semantic, symbol-level namespace check backstops the reference list**
  (`QueryCompiler.EnsureNoSandboxedNamespaceUsage`), because assembly omission alone cannot exclude
  types that are physically defined inside an always-required core assembly. After a successful
  emit, the compiler walks every identifier resolved within the **user-authored** region of the
  generated source (the compiler-generated wrapper scaffolding is skipped, using
  `GeneratedUserQuerySource.QueryHeaderLineCount` to find where user text starts) and resolves each
  to its `ISymbol` via the `SemanticModel`. Any symbol whose containing namespace starts with
  `System.IO`, `System.Net`, `System.Diagnostics`, `System.Reflection.Emit`,
  `System.Runtime.Loader`, `System.Runtime.InteropServices`, or `System.Threading` (excluding the
  allowed `System.Threading.Tasks` subtree, needed for the generated wrapper's own
  `SaveChangesAsync` overrides) causes compilation to fail with the same sanitized
  `QueryExecutionException` used for ordinary binding errors — the query author sees "could not be
  compiled," not a stack trace or a distinct "blocked API" signal. This is what actually stops
  `System.IO.File.ReadAllText(...)` and `System.Reflection.Emit.AssemblyBuilder.DefineDynamicAssembly(...)`,
  neither of which the reference list alone can exclude. Text-scanning the raw query string was
  considered and rejected in favor of this approach: naive text scanning is trivially bypassed
  (string concatenation, `Type.GetType` with a fully-qualified name, etc.), whereas resolving
  actual bound symbols via the semantic model is not, because it reflects what the compiler itself
  determined the identifier refers to.
- **`unsafe` stays hard-disabled** (`allowUnsafe: false`) — this is the one language feature that
  can defeat reference-list containment (arbitrary memory access can, with enough effort, forge
  references to types/methods never referenced), so it is the one thing this plan does *not*
  relax regardless of the user's broader direction, because it stops the containment strategy
  itself from working, not just a feature.
- **Compile timeout and query/command timeout stay enforced**, same as today, to bound both
  malicious and accidentally-pathological input.
- **Connection policy (production/`ReadOnly` rejection for anything mutation-capable) stays
  enforced** — this predates this rewrite and is unrelated to the parser choice; it isn't relaxed.
- **Sanitized error responses stay enforced** (see [Error sanitization](#error-sanitization)) —
  relaxing *what LINQ you can write* is unrelated to *what a stack trace may disclose*.
- **`run_query` mutation capability (`SaveChanges()` etc.) stays off by default**, gated behind
  the `QueryExecution:AllowMutationsInRunQuery` flag from
  [Change tracking](#change-tracking--mutation-scope--saveChanges) — this
  is the one place this plan intentionally does *not* immediately grant everything the inheritance
  model exposes, because `run_query` is documented today as read-only and changing that default
  silently would be a behavioral break, not a safety-model judgment call. Enabling it is a
  follow-on decision the user can make explicitly later (tracked in [Open items](#open-items)).

In short: the *query surface* becomes as permissive as real C#, matching the user's ask and the
LINQPad model exactly, while the *blast radius* is bounded by what assemblies are visible to the
compiler (a much stronger and simpler control than an ever-growing operator allowlist ever was) —
not by trying to restrict the language itself, except for the single `unsafe` carve-out that would
otherwise undermine that control.

## Behavioral parity notes

- **`GetType()` returns `UserQuery_{token}`, not `TContext`.** If any query author relies on
  `GetType()`/`GetType().Assembly` to mean "my `DbContext`'s assembly," that will now return the
  compiled-query assembly instead — exactly the same surprise LINQPad's own docs call out (see
  the attached reference notes). Document this in the rewritten `query-execution.md` rather than
  trying to hide it (e.g. by overriding `GetType()`, which isn't possible — it's `sealed` on
  `object`).
- Custom properties/methods on the target `DbContext` (e.g. a `RecentOrders` computed
  `IQueryable<Order>` property) become directly callable from query code for free, matching the
  reference notes' example — this was not possible at all under the Dynamic-LINQ model and is a
  direct example of the "whole area of things" the user is asking to unlock.

### Result-shaping scope: only `IQueryable` results are shaped into rows

`RoslynQueryExecutor.ShapeResultAsync` only performs its capped materialize-and-project pipeline
(row shaping, `Take`-cap enforcement, timeout-aware execution) when the compiled query's return
value is an `IQueryable`. Every other return value — including a plain `IEnumerable` produced by an
operator with no SQL translation (`Zip`, most notably; also `Enumerable`-only overloads reached
after an explicit `AsEnumerable()`/`ToList()`), an already-materialized list, or a genuine scalar
like `int`/`bool`/`string` — is returned as-is through the `QueryResult.Scalar` slot with
`IsScalar = true`.

This was a deliberate decision, not an oversight:

- `IQueryable.Expression` gives `GetEffectiveTake` an expression tree to search for a user-supplied
  `Take(n)` call, so the cap in `QueryExecutionOptions.MaxTake`/`DefaultTake` can be applied via
  provider translation *before* the database is asked to produce any rows. A plain `IEnumerable` has
  no expression tree — by the time `ShapeResultAsync` sees it, if it's driven by an iterator it may
  already be too late to bound how much work executing it does, and if it's already a realized
  collection it has already been fully materialized without a cap at all. Neither case can be capped
  consistently with how `IQueryable` results are capped.
- Query authors who want `Zip`/other non-translatable-operator output shaped into rows can end the
  query with `.ToList()` (or any other terminal operator) and read the result via the `Scalar` slot;
  the object is still fully returned to the caller, just not row-shaped. This mirrors how LINQPad
  itself dumps the raw object graph for non-`IQueryable` results rather than pretending they're
  paged query results.
- Because of this, the `DbContext context` parameter that `ShapeResultAsync` used to accept was
  unused (row shaping only needs the `IQueryable`'s own `Provider`) and has been removed.

See `RoslynQueryExecutorTests.ExecuteAsync_Zip_PairsTwoRootsPositionally` for a test that exercises
and pins this behavior.

## Compiled-query caching (later)

Out of scope for the current implementation, but worth recording as a deliberate non-goal for now:
since compilation cost is paid per request, a follow-on optimization could cache compiled
`UserQuery_{token}` assemblies keyed by `(contextName, normalizedQueryText)` inside a bounded LRU,
provided the target assembly hasn't been reloaded since (tie cache invalidation to
`AssemblyReloadWatcher`, which already exists for detecting target rebuilds). Not needed for
correctness — only raised here so it isn't rediscovered as a surprise later and mistaken for a
required part of the core Roslyn pipeline.
