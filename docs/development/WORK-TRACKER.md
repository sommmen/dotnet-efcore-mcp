| P1 #14 — keyset/cursor pagination | [Query execution](./query-execution.md) · [MCP tools](./mcp-tools.md) | Add an opt-in `pagination: { mode: "cursor", cursor?: string }`/`nextCursor` keyset-paging mode to `run_query`, mutually exclusive with `skip`. Require a unique deterministic order by auto-appending the primary key as a tie-breaker; encode cursors as opaque tokens bound to entity/context/ordering shape and reject malformed, mismatched, or tampered cursors without disclosing decoded values. Scope v1 to forward-only paging. Keep coexisting with `take`/`hasMoreRows` (P0 #2) and legacy offset `skip`/`take` paging, which stay fully supported when `pagination` is omitted. Cover parity, issuance/resumption, tie-breaking, rejection cases, and `hasMoreRows`/`nextCursor` agreement with focused tests. |
| P0 #1 — Roslyn-compiled `UserQuery` engine cutover (supersedes Dynamic-LINQ `run_query`) | [Roslyn-compiled `UserQuery`](./roslyn-user-query.md) · [Query execution](./query-execution.md) · [MCP tools](./mcp-tools.md) | The Roslyn compilation pipeline (a generated `UserQuery_{token} : TDbContext` class, mirroring LINQPad's own EF Core driver model) is implemented, registered behind an `Engine = DynamicLinq|Roslyn` toggle, and fully covered by tests — including the ported `QueryExecutorTests` cases and new tests for previously-impossible shapes (`Join`/`GroupJoin`/`SelectMany`/`Zip`, statement-block queries, reference-list containment). Remaining work is the cutover itself: flip the default engine from `DynamicLinq` to `Roslyn`, then remove `System.Linq.Dynamic.Core` and the old expression-tree-building code. See the linked plan doc's "Migration / rollout plan" for the remaining steps. |
| P0 #4 — `preview_query_sql` | [Query execution](./query-execution.md) · [MCP tools](./mcp-tools.md) | Add a read-only generated-SQL preview tool for both legacy structured and arbitrary-LINQ `run_query` request forms. Route execution and preview through one validated query-builder pipeline; the preview calls EF Core `ToQueryString()` only and must not enumerate, open a connection, execute a command, or persist changes. Return sanitized SQL without caller parameter values, provider exceptions, connection strings, or stack traces. Cover request equivalence, provider-specific SQL generation, the non-execution guarantee, and sanitization. |
| P0 #6 — schema slicing/search | [Schema / model discovery](./schema-discovery.md) · [MCP tools](./mcp-tools.md) | Add cache-only `get_entity_schema(contextName, entityName)` for one full cached entity definition and cache-only `search_schema(contextName, query, maxResults?)` for capped, compact entity/property/relationship matches. Cap `maxResults` at 25 (default 10); preserve a stable result order and report truncation. Design request routing so a future access-policy evaluator can restrict the cached result set before matching/slicing without changing either public response shape. Cover cache-only behavior, matching, caps/truncation, validation, and future-policy seam forwarding. |
| P0 #5 — `test_connection` diagnostics | [Connection management](./connections.md) · [MCP tools](./mcp-tools.md) | Add a server-registry-only diagnostic tool accepting `contextName` and optional `connectionName` (otherwise the active connection). Construct only the requested context with the resolved entry and perform a bounded connection-health check; honor the MCP cancellation token and the entry command timeout. Return only redacted logical metadata and a stable success/failure classification—never a connection string, credentials, provider exception text, inner exceptions, or stack trace. Keep it non-mutating and unable to accept arbitrary connection strings; cover success, unknown/inactive connection, context-construction failure, timeout, cancellation, and redaction. |
| P0 #7 — query complexity limits beyond row count | [Query execution](./query-execution.md) · [MCP tools](./mcp-tools.md) | Add server-wide legacy-field caps (`MaxWhereLength`, `MaxOrderByTerms`, `MaxIncludeCount`) plus arbitrary-LINQ expression-length, syntax-tree depth/node-count, and operator-count caps to `QueryExecutionOptions`. Validate before EF translation or database access; reject unsafe complexity with a sanitized `QueryExecutionException` that names only the limit and maximum. Apply identical enforcement to `run_query` and `preview_query_sql`, and test each boundary, combined violations, and no parsing/provider access after rejection. |
| P0 #8 — database-side `run_query` collection-include cap | [Query execution](./query-execution.md) · [MCP tools](./mcp-tools.md) | Make `MaxIncludedCollectionItems` a per-parent, database-side cap: translate each requested collection include to ordered filtered-include SQL (or an equivalently bounded split-query plan) with a per-collection `Take`, before materialization. Do not truncate already-loaded navigation collections. Keep reference includes, root paging, and the one-level include contract unchanged; cover per-parent behavior, zero/exact/below-cap boundaries, deterministic ordering, root paging, and SQL/command evidence that child rows are limited before materialization. |
| P2 #15 — named multi-target assembly registry | [Multi-target assembly registry](./assembly-registry.md) · [Assembly loading](./assembly-loading.md) · [MCP tools](./mcp-tools.md) | Let the server hold several compiled assemblies loaded at once, each under a stable logical `targetName`, instead of one implicit target. Extend `load_assembly` and add `list_loaded_assemblies`/`select_target`; add optional `targetName` to `list_contexts`/`get_schema`/`run_query`/`run_sql_query`, defaulting to the current target when omitted so existing single-target callers see no behavior change. Give each named target its own isolated collectible `AssemblyLoadContext` and reload watcher; `SchemaCache`'s `Type`-keyed cache already isolates correctly across targets with no rework. Leave per-connection `AccessPolicy` (P0 #9) unchanged — it stays scoped to the selected connection, independent of which target resolved the `DbContext`/entity name. Cover multi-target isolation, name collisions, unknown-name rejection, default-target backward compatibility, per-target reload, and access-policy composition with focused tests. |
| P2 #16 — out-of-process query host pooling | [Out-of-process query host pooling](./query-execution-host-pooling.md) · [Query execution](./query-execution.md) | Measured `run_query` under `QueryExecution:Mode=OutOfProcess` at ~1.6–2.1s/call, dominated (~1.0–1.4s) by per-call Roslyn compilation of the generated query source in a cold process, not by `dotnet exec` startup (~90–250ms). A PoC persistent-host process reusing warm JIT/Roslyn state cut per-query latency after the first by ~15–20x (to ~65–130ms). Add an opt-in `QueryExecution:Mode=Pooled` executor: a small bounded pool of long-lived query-host workers keyed by target-assembly identity, with a hard per-query timeout that kills and drops a hung/failed worker, and periodic recycling after N served queries to bound memory growth and staleness — keep `Auto`/`OutOfProcess` as the unchanged default until the pooled path has field experience. See the linked design doc for the full tradeoff analysis and rollout/testing plan. |

## Adding new work

When starting new feature work or discovering a gap:

1. Add a row to the table above (or a new table/section if the work doesn't fit an
   existing area) describing the item and linking to the relevant slice doc.
2. If the work is substantial enough to need its own reference documentation, add or
   extend a slice under [`docs/development/`](.) and link it from
   [`DEVELOPMENT.md`](../../DEVELOPMENT.md).
3. Once the work lands, move the checklist detail into the relevant slice document (with
   implementation notes, as the existing slices do) and remove the row from this table.
